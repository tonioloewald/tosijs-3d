## Minor

### Verified

1. **The headset chase HUD plane is orphaned, still enabled, when the aircraft is removed** (correctness, `src/b3d-aircraft.ts:2519`, severity uncertain).
   - The XR chase HUD is now parented to the chase anchor (line 1152). `sceneDispose` un-parents every child of that anchor and then disposes it, so the plane survives at roughly world (0, 1.7, 2.3) and its SvgTexture keeps rasterising every 50 ms.
   - This is a regression: before the diff the plane was a child of the airframe node and was disposed with it.
   - The lens reproduced it in the emulated headset; the verifier confirmed it by reading the code and did not re-run the reproduction.
   - In the normal death-then-respawn flow the orphan lasts only until the new craft's first HUD mount disposes the old plane. It persists when a player aircraft is removed without a replacement while `<tosi-b3d-hud>` stays mounted (vehicle swap, return to menu, custom `choices` flow).
   - Fix: in the aircraft's `sceneDispose`, call `this._hud?.setInSceneVisible?.(false)` and clear `_hudMountKey`, or have the un-parent loop skip non-rig children.
   - Check that clears it: the same emulator run on `/b3d-aircraft/`, with `hud-3d` absent or disabled after `aircraft.remove()`.

2. **The gamepad step-aside only reaches a pad nested inside `<tosi-b3d>`, but the gamepad page's demo mounts it as a sibling** (blast-radius, `src/tosi-b3d.ts:1303`, severity uncertain). This merges the correctness nit on the same lookup.
   - `_suppressGamepad` uses `this.querySelector('tosi-b3d-gamepad')`, which finds only the first descendant pad and silently does nothing on a miss.
   - The demo at `src/glass-gamepad.ts:74` appends the pad beside the scene. For that placement the new doc snippet `scene.querySelector('tosi-b3d-gamepad')` returns null, so `pad.suppress('shop')` throws.
   - manta-recon is covered: it mounts with `gamepad: true`, which appends the pad as a light-DOM child.
   - Consumers who copy the sibling placement get the pre-change behaviour, so this is not a regression for them.
   - The verifier confirmed this by reading the code; nothing was run in a browser.
   - Fix: at minimum, qualify the doc and changelog ("applies to a pad inside the scene element") and have the snippet use the `pad` reference the reader already holds. Better, have pads register with the scene they serve and walk that set.

### Unverified (leads; sanity-check before acting)

3. **(unverified) None of the six behavioural changes has a test that fails without it** (correctness, cross-cutting). This merges the blast-radius nit about the popup stacking fix.
   - The diff changes no test file. Untested: the three popup stacking faults, the two `climbCost` formulas published in the attribute table, and the pad's named-reason suppress set and `poll()` gate.
   - Cheap pure tests first:
     - fly-by-wire: full throttle at pitch p settles at `maxSpeed*sqrt(1 - diveBoost*sin(p)/accel)`, and `diveBoost` 0 makes a climb free.
     - glass-gamepad: suppress and release with two reasons, and `poll()` returning empty while suppressed.
     - popup: extract the per-popup offset step as a pure function beside `modalPickable`, and pin "restack twice in one frame" and "restack after `place()`".
   - Otherwise add the popup fix to #3236 so the debt is counted.

4. **(unverified) `tearOff` moves a popup into world space but leaves `stackLift` in the old parent's space** (correctness, `src/popup-surface.ts:994`).
   - The lens reasoned this from the code and did not reproduce it.
   - The next restack would subtract a parent-space vector from world coordinates: millimetres for tilt alone, centimetres times stack depth on a panel scaled well below 1.
   - `place()` clears `stackLift` in the equivalent case; `tearOff` does not.
   - Fix: clear or convert `stackLift` in `tearOff` before `setParent(null)`.

5. **(unverified) XR chase HUD size assumes the unzoomed chase seat** (correctness, `src/b3d-aircraft.ts:1155`).
   - The plane is sized for a viewer at `chaseDistance * 0.8`, but the rig sits at `chaseD * (0.8 + chaseZoom * 1.1)`.
   - Zoomed fully out, the HUD would cover under half the promised angle, and the mount key ignores zoom so it never corrects.
   - Fix: either say the match holds at default zoom, or include the rig's back distance in the size and the mount key.

6. **(unverified) The step-aside is wired to pause and death by name, not to the library's modal surface** (blast-radius, `src/popup-surface.ts:1062`).
   - A touch consumer who opens `openPopup({ modal: true })` (shop, dialogue, settings) would hit the bug manta reported and have to find `pad.suppress()` themselves.
   - Fix: call `owner._suppressGamepad('popup-modal', anyModalOpen)` from `applyModalBlocking`. If deferred deliberately, record it on the board so pause and death are not read as the complete fix.

7. **(unverified) The two changelog items marked (behaviour) do not say how to opt out** (blast-radius, `CHANGELOG.md:40`).
   - The HUD entry does not mention that `hudChaseOff` keeps the chase view bare.
   - The gamepad entry has no opt-out, and per the lens none exists in code.
   - Fix: add one clause to each entry. For the pad, either name the way to keep it or say there is none yet; a `stepAside="off"` enum attribute would be the smallest opt-out.
