## Blockers (must be fixed before the tag)

### B1 — The budgeted terrain rebuild leaves every retained tile cut at the OLD `tileSize` and OLD world position when a grid-shaping attribute changes, and reports itself finished
`src/b3d-terrain.ts:1278` (`streamTiles` placed-match branch) — **confirmed, adversarially verified**

`streamTiles`'s placed-match branch copies only `priority` from the desired cell onto a retained tile; `cell.tileSize`, `cell.cx` and `cell.cz` keep whatever the tile was last built with. `cellKeyNum(level, gx, gz)` omits size, so an old cell key-matches a desired cell that is now a **different size at a different place**, `covered.add(k)` then suppresses the blank that should have filled the true location, and `generateTileMesh` re-cuts from the stale cell (`mesh.position.set(cell.cx, 0, cell.cz)`, `:1560`).

This is a **new** regression, not a latent one: every generation-key change used to go through `render()` → `regenerate()` → `clearPool()`, which freed all cells so nothing was ever retained. The diff replaces that with `_rebuild(false)` → `markPoolStale()` (`:1776`, `:1803`), which retains.

Measured headlessly against a NullEngine (camera at origin, 400 frames drained):

- `tileSize` 20 → 40 (lodLevels 4, reach 600): **74 of 80** placed cells violate `cell.tileSize === base·2^level` / `cell.cx === (gx+0.5)·tileSize` — e.g. `{level:1, gx:-2, tileSize:40, want:80, cx:-60, wantCx:-120}` — with `stale` back to 0, i.e. the streamer believes it is done.
- `horizScale` 1 → 2 (tileSize 80, lodLevels 5): **all** placed tiles wrong; a realistic 40-frame drag-then-settle: 68 of 68 wrong, no stale tiles remaining.
- The same change via `regenerate()`: **0 wrong.** The two paths now disagree about what the world is.
- Control (`grossAmplitude`, height-only): 0 wrong — the budgeted path is correct for exactly the case its tests cover.

Not self-healing for a stationary camera; it clears only once the camera travels far enough that every old cell leaves the desired set. `terrainEditor3d`'s doc demo uses a fixed orbit camera, so that escape does not apply.

Reachable from shipped code with no adopter involvement: `horizScale` is in `terrain-editor.ts:143`'s always-shown **shape** group (labelled "horizontal size"), `tileSize` is in `advanced` (`:149`), and that editor's doc demo deliberately does plain attribute writes — "Ordinary attribute writes. The element regenerates itself on change." Dragging that slider yields gapped, wrong-scale terrain that never converges and never errors.

**Remediation** — either:

- (a) copy the **whole** desired cell onto the retained tile in the match branch (`tileSize`, `cx`, `cz` as well as `priority`) and set `t.stale = true` when any of those changed, so the stale pass re-cuts it at the right size and place; or
- (b) split `_generationKey()` so grid-shaping attributes (`tileSize`, `horizScale`) take the unbounded `clearPool` path while height-only attributes take the budgeted one.

**And add the regression test the suite lacks** (this is finding M1 below, folded in): after a `tileSize` change and after a `horizScale` change plus a full drain, assert for every placed tile that `cell.tileSize === attrs.tileSize * attrs.horizScale * 2**cell.level` and `cell.cx === (cell.gx + 0.5) * cell.tileSize`.

**Re-review scope:** correctness + blast-radius over the remediation diff only (`b3d-terrain.ts` `streamTiles`/`_rebuild`, plus the new test), and a re-run of `terrain-regenerate`, `terrain-budget`, `terrain-grid`.

*Adjacent observation noted during verification (not part of the finding, do not scope-creep the fix): `stale` is cleared only in `generateTileMesh` and `clearPool`, so a tile freed while stale keeps the flag, and a pool-wide `some(t => t.stale)` drain check can never settle.*
