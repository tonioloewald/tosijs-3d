## 🔴 Blocker (must be fixed before the tag)

### B1 — The shipped CHANGELOG's ⚠️ Breaking block contradicts its own Fixed block *and the code*
`CHANGELOG.md:35-36` — **verified twice, independently.**

The 0.8.0 ⚠️ Breaking block says:

> Not yet renamed (still `onX`, and unaffected): `inputField`, `keyboard`, `table`, `box`/`surface`.

Sixty lines below, the same entry's Fixed block says the opposite, and the code sides with Fixed: `handlerOf` is imported and called in `src/table.ts:171,267,269`, `src/box.ts:257,294,1016`, `src/surface.ts:168,614`, `src/keyboard.ts:280,720,722,1300`. Every one of those options carries `@deprecated use handleX — removed in 0.9`. I saw the warning fire live during the test run: `src/surface.test.ts` printed ``tosijs-3d: `onSelect` is deprecated — use `handleSelect`.``

Provenance: the sentence was written at `71613e13`; `da1cf072` did the migration and added the Fixed bullet without updating it.

**Why blocker rather than major.** It is not merely wrong — it is the *only* upgrade-facing statement of this release's headline change that reaches a consumer as guidance, because `Migration.md` (M1) has no 0.8.0 section. It ships in the npm tarball (`files` includes `CHANGELOG.md`) and is already pre-rendered onto the public site (`docs/CHANGELOG/index.html`). A consumer reads the ⚠️ block — that is what it is for — concludes those five widgets are exempt, and is told to *disregard* the very deprecation warning that would otherwise have saved them at 0.9.

Mitigations that keep it from being catastrophic (and are why the correctness verifier argued for major): both spellings work in 0.8.x, the runtime warning names the exact replacement, and the correct list is present in the same entry. But a document that pre-emptively tells you a warning does not apply to you actively undermines its own mitigation.

**Fix:** delete or invert `CHANGELOG.md:35-36` — e.g. "Migrated in this release: `inputField`, `keyboard`, `table`, `box`/`surface` — see Fixed." One line. Re-review scope: **Tier 0 only** (mechanical doc edit, no code touched).

## 🟠 Majors — fix before the tag

### M1 — `Migration.md` has no 0.7.8 → 0.8.0 section *(verified)*
`Migration.md:12` — the file's only heading is `## 0.6.2 → 0.7.0`; `git diff v0.7.8...HEAD -- Migration.md` is **empty** across a 770-file diff. Meanwhile `README.md:9` points consumers at it as the authoritative breaking-change list, so its silence implies 0.8.0 has none.

This breaches an explicit rule: `RELEASING.md:87` — *"A peer-dependency break … MUST be called out in the changelog + migration note."* The changelog half was done; the migration half was skipped. The peer floor genuinely moves `tosijs ^1.7.8` → `^1.9.2`.

One correction to the finding as filed: the "npm ERESOLVE means the in-package copy is unreachable" argument is self-defeating (if install fails, the tarball is never unpacked). The in-package copy earns its keep for bun/pnpm (warn-and-proceed), `--legacy-peer-deps`, and post-install behavioural surprises — notably that a wrong-typed `initAttributes` write now warns-and-applies instead of being silently discarded (use `isOff()`).

**Fix:** add `## 0.7.8 → 0.8.0` with two entries — the peer bump + its behaviour change, and the `onX` → `handleX` table with the 0.9 removal. Both bodies already exist in CHANGELOG.

### M2 — The flagship `/ui/` demo teaches `onX`, and its `iconGrid3d({ onSelect })` is silently dead *(verified)*
`src/docs/ui.md` — confirmed: `onChange` at lines 61, 75, 76, 81, 84; `onSelect` at 88; `onClick` at 92, 93. The file *was* edited in this diff (its toc now links to the new `/handler-of/` page) but the demo body was not — so the page links to the deprecation notice while violating it.

Two distinct costs:
- **(a)** `toggle3d` and `slider3d` call `handlerOf` in the factory body, so the deprecation warnings fire at **page load**, not on interaction. Every visit to https://3d.tosijs.net/ui/ prints them, on the page documenting the rule.
- **(b) Worse:** `grep -c handlerOf src/icon-grid.ts` → **0**, and the module contains no `onSelect` at all — only `config.handleSelect?.(…)` at line 503. So `iconGrid3d({ onSelect })` is not deprecated-but-working, it is **ignored with no warning**. The highlight still moves (`draw()` runs), but the callback never fires, so `state.tool` never updates. That is precisely the silent-dead-callback class this release was cut to eliminate, sitting on the page announcing the fix.

Not a regression from this diff — `v0.7.8:src/docs/ui.md` already had it; `b3f55a32` renamed icon-grid's callbacks and missed this file. And `iconGrid3d.onSelect` never shipped in a published release, so there is **no back-compat obligation** — the fix is the doc line, not a shim in the widget.

**Fix:** rewrite the kitchen sink to `handleChange`/`handleClick`/`handleSelect`. Optionally add `handlerOf` to `icon-grid` so the blanket "every `onX` still works" promise is true of it too — but the demo must not pass a key the widget never reads.

### M3 — The panel-sizing guess just proven wrong in a headset survives verbatim in two other panels *(verified)*
`src/tosi-b3d.ts:1103` (pause modal) and `src/b3d-death.ts:721` both still compute `const svgH = 46 + rows.length * 48` — the exact formula `56e8462e` removed from `B3d._makePanel` after it crammed `lightEditor3d` (one row, ~1183px of layout) into ~142px. `panel3d`'s `height` already **defaults to `'fit'`**, so both sites actively override a correct default with the discredited guess.

Both take **consumer-supplied** rows (`pausePanel(host, resume)`, `choices()`), both render as in-scene planes in an immersive session, and the death panel is by construction the one you cannot navigate away from. No test covers either twin; the fix cannot propagate on its own.

⚠️ **This is not "delete the override."** `svgH` is reused at each site to set the world-plane aspect (`tosi-b3d.ts:1152`, `b3d-death.ts:748`), so a correct fix must build the SVG, read the resolved height back off the element, and pick a `maxHeight` suited to a camera-relative plane (620 was tuned for the gear panel; an uncapped `'fit'` on a 1200px editor is a ~4-world-unit plane in your face). Three sites, three caps — factor `_makePanel`'s config into one shared helper so the policy lives in one place.

### M4 — `"./*"` publishes the whole `dist/` tree as semver-committed public API *(verified)*
`package.json:20`. Verified empirically under Node 24: `tosijs-3d/reflections`, `tosijs-3d/dynamic-shadows` and `tosijs-3d/rippling-water` now resolve with full types — the three modules CLAUDE.md marks "superseded … not exported from index.ts." Under v0.7.8's exports map they correctly failed with `ERR_PACKAGE_PATH_NOT_EXPORTED`. They carry no `@deprecated`, no doc comment, and no `llms.txt` entry, so an editor auto-import or an agent scanning `dist/*.d.ts` finds them with zero signal.

Tempering the headline: 142 of the 153 modules were already public via the barrel, so the genuinely-new surface is **9 modules**, 3 of them dead. The semver half of the claim stands in full — every filename is now a supported specifier and nothing in the build or tests would notice a rename.

**Fix (verified to work):** add `"./reflections": null, "./dynamic-shadows": null, "./rippling-water": null` **above** the `"./*"` entry — I confirmed this restores `ERR_PACKAGE_PATH_NOT_EXPORTED` for those while `tosijs-3d/curve` still resolves. Also fix `CHANGELOG.md:155`, which describes this as "`tosijs-3d/light-settings` now works" while shipping a wildcard over all of `dist/`.

## Follow-ups — file to `TODO.md`

> Findings marked *(unverified)* were reported by a lens and not adversarially verified. I spot-checked the **code claim** of each against the source and confirmed it; the failure scenario has not been independently stress-tested. Sanity-check before acting.

**Correctness**

- [ ] **`table` button-column menu anchored with the COLUMN gap as a vertical offset** *(unverified — code claim confirmed)*. `src/table.ts:749` uses `y: HEAD_H + GAP + i*ROW_H - scroll`, but the body layer is drawn at `translate(0, HEAD_H + 2)` (:525) and hit-tested with `y - (HEAD_H + 2)` (:546). `GAP = config.gap ?? 8` is the **column** gap, passed to `resolveColumns` at :522. At defaults the menu opens 6px low; `gap: 0` → 2px, `gap: 24` → 22px. Error scales with a setting unrelated to vertical layout, so it reads as random. Hoist `HEAD_H + 2` into a named `BODY_TOP` so the three sites cannot drift again.
- [ ] **`panel3d` never gives `header` widgets a `WidgetHost`** *(unverified — code claim confirmed)*. `src/widgets3d.ts:2585` does `widgets.forEach((w,i) => w.setHost?.(hostFor(i)))`; `headerWidgets` (:2233) is never visited. Any pinned widget needing a host is inert — `select3d`'s dropdown, `button3d({menu})`, `iconGrid3d` menu cells, the new table button column. Latent today (the only in-tree header is `iconBar3d`, which needs no host). Note the trap: `hostFor(index)` uses the **body** offsets and subtracts `scroll`, so the naive fix anchors header popups at a scrolling row. Add a `headerHostFor(index)` using `headerLayout.offsets[index]` with no `- scroll`. If pinned popups are out of scope for 0.8.0, say so on the `header` JSDoc rather than failing quietly.
- [ ] **Three deprecation policies ship in one release; two disagree with the documented one** *(unverified — code claim confirmed)*. `handler-of.ts` states the rule: new name wins, old is NOT called, warns once. But `src/b3d-trigger.ts:270-271` calls **both** `this.whenEnter?.()` then `this.onEnter?.()` (same at :280-281), with no warning — a consumer who adds `whenEnter` while an old `onEnter` is still live gets the handler run twice per crossing. And `src/theme-editor.ts:193` uses `(handleChange ?? onChange)?.(w3dTheme)`, so its `onChange` is `@deprecated` in the types but **never warns at runtime**. Make the trigger `this.whenEnter ?? this.onEnter` + warn; switch themeEditor to `handlerOf`. If `handlerOf`'s signature doesn't suit `when*`, add a sibling helper — the point of extracting `handler-of.ts` was one answer to this question.
- [ ] **An icon name colliding with an `Object.prototype` key throws instead of falling back** *(verified)*. `src/svg-icons.ts:238` — `data[cur]?.trim()` against a plain object walks the prototype chain; `?.` only guards null/undefined. `iconGlyph('constructor'|'toString'|'valueOf'|'hasOwnProperty'|'__proto__')` throws `TypeError: data[cur]?.trim is not a function`. This release is the **first** where a table data value becomes an icon name (`src/table.ts:479,497` do `iconGlyph(String(row[c.key]))`, both new lines in this diff), and there is no `catch` anywhere in the repaint path — so scrolling a virtualized row onto screen kills the body build, in a VR panel with no console. Fix: `Object.hasOwn(data, cur) ? data[cur] : undefined` (or build the maps with `Object.create(null)`) plus a `typeof === 'string'` guard. `register-icons.test.ts` pins hostile *values* but no hostile *names* — add that case.
- [ ] **`zeroStop` silently discards `step` on a log slider** *(unverified — code claim confirmed)*. `src/widgets3d-layout.ts:416` — the zeroStop branch returns before the `step > 0` decade quantisation applied at :428-429, honouring only `snap`. `slider3d({scale:'log2', step:1, zeroStop:true, min:1, max:256})` loses its octave stepping with no error and no doc note. Either quantise the exponent inside the branch, or document the mutual exclusion on the `zeroStop` JSDoc (`src/widgets3d.ts:1417`, which currently only discusses `min`). Pin whichever in `slider-scale.test.ts`.

**Security**

- [ ] **`registerIcons` is an unsanitized markup-injection sink with no stated trust requirement** *(unverified)*. `src/svg-icons.ts:429` → values injected via `holder.innerHTML = spec` (:271, and again at :524 in `iconGlyph`), children then moved into a live `<svg>` appended to the document. The `<script>` is inert (fragment-parsed), but an `onerror=` attribute survives and fires. The new doc text markets this as "the answer to 'I have icons I do not want to push upstream'" and says nothing about provenance. Either state the boundary in the JSDoc *and* the doc-comment section, or warn-and-drop entries containing `<script`, `<foreignObject` or any `on*=`. Add a test pinning whichever guarantee you make.

**Efficiency**

- [ ] **`spinner3d` registers into a module-global ticker no panel path can unregister** *(verified, reproduced)*. `src/widgets3d.ts:1917` adds to a module-global `spinners` Set + shared 60ms `setInterval`; the only exit is the returned `dispose()`, but `Widget3d` (:603-666) has **no `dispose?()` member** and nothing in the repo ever disposes a widget. `B3d._panelWidgets()` (`src/tosi-b3d.ts:2621`) re-invokes `scenePanel(this)` on every `_repaintPanels()` — pause/resume, every icon-bar toggle, every gear open (call sites: 1009, 1034, 2366, 2435, 2452, 2562, 2606, 2805), plus `_setupScenePanel()` (:4038) which builds widgets purely for a `.length` check and throws them away. Verified with happy-dom: 5 orphaned spinners all still ticking 200ms later; the interval can never reach `size === 0`. Each entry also retains its whole SVG subtree via the tick closure — a memory leak, not just wasted CPU. Cheapest fix: drop any entry whose `el.isConnected` is false at tick time (3 lines, no API change). `spinner3d` is new in 0.8.0 with no adopters, so the contract is still free.
- [ ] **The `w3d-theme` demo observes the whole document subtree to detect its own unmount** *(unverified — code confirmed)*. `src/w3d-theme.ts:50` — `observe(document.body, {childList:true, subtree:true})` on a page hosting many live `<tosi-b3d>` demos means every node insert anywhere enqueues the callback. Body is cheap (`if (preview.isConnected) return`), so it's microtask churn, not visible cost. Fix: `observe(preview.parentNode ?? document.body, {childList: true})` — dropping `subtree` is the whole change. The restore-on-unmount behaviour is right; only the scope is over-broad.
- [ ] **Note in `light-modulation.ts` that the repeated `segmentTimes`/`splits` derivation is measured-free** *(second-order, from a refuted finding — see below)*.

**Blast radius / API hygiene**

- [ ] **The new import-extension guard covers only relative specifiers** *(unverified — code confirmed)*. `src/import-extensions.test.ts:56` — the regex is `/\bfrom\s+['"](\.\.?\/[^'"]*)['"]/g`, matching only `./`/`../`. But the 0.8.0 CHANGELOG names **two** halves of the ERR_MODULE_NOT_FOUND fault, the second being deep package subpaths (`@babylonjs/core/Misc/observable.js`). All 13 current deep Babylon imports happen to carry `.js`, so the tree is clean — but the next `from '@babylonjs/core/Meshes/mesh'` passes the suite, passes tsc (`tsconfig.build.json` sets `moduleResolution: "bundler"`, which is exactly why the original 394 were never flagged), passes every bundler, and re-breaks Node for consumers. Extend the guard to bare specifiers with a path segment (skipping package roots), **or better** move `tsconfig.build.json` to `"moduleResolution": "nodenext"` so the compiler rejects both halves — the toolchain being the guard beats a regex kept in sync by hand.
- [ ] **Three widgets still import `handlerOf` from `widgets3d.js`** *(unverified — code confirmed)*. `src/vector-field.ts:101`, `src/footprint-field.ts:47`, `src/curve-field.ts:330`. `handler-of.ts`'s own doc gives the rationale — "in its own module so the smallest widget can adopt it without dragging `widgets3d` into its import graph" — and every other adopter (`keyboard`, `surface`, `table`, `box`, `tosi-b3d`) already imports from `./handler-of.js`. For `footprint-field` it is the **only** runtime value taken from widgets3d. This matters more now that `./*` shipped: `import { footprint3d } from 'tosijs-3d/footprint-field'` is a supported path that transitively loads widgets3d + w3d-theme — the opposite of what per-module subpaths are for. Three one-word edits.
- [ ] **`themeEditor()` and `registerIcons` are page-global mutations with no library-level undo** *(unverified)*. The "theme editor infects other demos" fix landed in the **demo doc-comment**, not the library: a consumer putting `themeEditor()` on a settings route gets the identical bug, and the remedy they will copy is the demo's body-wide MutationObserver. Give `themeEditor()` a `dispose()`/`restore()` that snapshots the table at construction, and rewrite the demo to use it so the doc teaches the supported pattern. (`withTheme` is the wrong tool — it restores on synchronous return, not unmount.) Same shape for `registerIcons`: a page-global mutable map, documented as silently replacing built-in names, with no `unregisterIcons` — either add one or document that registration is page-lifetime and irreversible so a consumer can decide before depending on it.

**Coverage / docs**

- [ ] **`scene-schemas.test.ts:8` cites a `no-dom.test.ts` guard that does not exist** *(unverified — confirmed: `ls src/no-dom.test.ts` → No such file)*. The property holds today, and headless importability is the stated reason both these modules and the new `"./*"` export exist — but nothing pins it. A future `import { iconGlyph }` into `scene-schemas` would break every consumer's headless validator with nothing failing here. Either write the test the comment promises (import each declared-pure module in a fresh subprocess with no DOM globals — `world-contract.deps.test.ts` is the pattern), or correct the comment. Related: `table-layout.ts:15` now type-imports `MenuAction` from `widgets3d.js` — erased today, one careless `import type` → `import` from dragging tosijs into the "pure geometry" module.
- [ ] **Write `reviews/0.8.0-pre-tag-gate.md`.** `reviews/` holds five 0.7.0 files and nothing for this cycle. This report is the content; the directory exists so the GO/BLOCK reasoning for a tagged release has a durable record.
- [ ] **Verify the published tarball, not just the repo.** `npm pack --pack-destination ../local-packages`, then `import` a few subpaths (`tosijs-3d`, `/light-settings`, `/scene-schemas`, and a deep Babylon-touching one) under plain Node in an empty dir. ## Follow-ups — shared practices (`tosijs-coding-practices`)

- [ ] **`practices/review.md` — state the diff basis explicitly, and exclude generated artifacts from lens scope.** Two independent lenses (efficiency and blast-radius) each spent a **blocker** on "committed `dist/`/`docs/` are one commit behind `src/`" — a state `RELEASING.md` pre-empts almost verbatim ("*expected to be stale/dirty on `main` between releases* … don't treat their staleness as a defect"). Both were correct about the bytes and wrong about the conclusion, and one built its argument on an inverted npm mechanism (it cited the *absence* of `prepack` as the reason stale code would ship; with no `prepack`, `npm publish` packs the on-disk tree, which is the *correct* rebuild). That two careful readers landed there independently says the guidance is unreachable from where a lens sits: the review runs on `git diff <base>...HEAD` and the lens is never told that (a) generated artifacts are out of scope and (b) the working tree, not HEAD, is what ships. Fix in the review doc and mirror into the `pre-release-review` skill's lens preamble.
- [ ] **`RELEASING.md` — add a doc/demo-corpus sweep step for any release whose headline is a rename.** M2 exists because `src/docs/ui.md` was edited (toc) without its demo body being checked against the rename the same release introduces, and no lens owned the docs corpus. A one-line grep gate ("if this release deprecates a spelling, grep `src/docs/`, `demo/` and every `/*# */` block for it") would have caught it and cost nothing.
- [ ] **`RELEASING.md` / CLAUDE.md — one `[release] vX` commit per version.** 0.8.0 has **three** (`71613e13`, `6c9bce0a`, `da1cf072`) and no tag, so the release's provenance is unreadable: nobody can say which tree 0.8.0 is, and any gate that ran ran against one of three different trees. B1 is a direct consequence — the stale sentence survived because the "release commit" happened before the work it describes.

## Refuted findings — not defects, but two left a real gap

Recorded so they are not re-raised, and because the second one has a residual worth keeping.

1. **"Committed `dist`/`docs` are stale → blocker"** (raised twice, by two lenses). Refuted: this is the mandated state at the step-5a gate and `RELEASING.md` explicitly says not to treat it as a defect. → surfaced as the practices follow-up above. One factual correction worth keeping in the record: `height:'fit'`/`maxHeight` were *already* in the committed `dist`; only `panel3d`'s `header` was missing.
2. **"`segmentTimes`/`splits` allocate ~12 objects per animated lamp per frame."** The reviewer's object count (12) and the before/after delta (+10 vs v0.7.8) are **exact** — the refutation is only of the consequence. Measured across both engines that matter: `gcEvents = 0` over 1,080,000 lamp-frames on V8 (escape analysis sinks every literal; still 0 with 20 deliberately polymorphic hidden classes), and JSC heap-object delta indistinguishable. **Residual, kept as a nit:** the polymorphic run showed a real ~25% CPU regression from deriving `segmentTimes` four times per frame — which at 20 lamps × 90Hz is 0.016% of one core. Not worth memoizing, but worth a comment saying so, or the next reader re-derives this whole investigation. → TODO item above.

## Completeness gaps — the release process, not the code

These are not findings against the diff; they are things the gate should do before the tag.

1. **Stop the dev server (pid 63837) and run a clean `bun run build` before committing `dist`/`docs`.** The working tree's rebuild came from the watcher, and committing during a wipe window is the documented way to take 3d.tosijs.net down.
2. **The XR half of `56e8462e` was never verified in a headset.** Its riskiest piece is `panel3d`'s pinned `header` — a fixed-y row over a scrolling body is two coordinate spaces, in the file that carries the scar of an XR panel silently becoming untargetable (ray → plausible uv → wrong control). `panel-fit.test.ts` pins the geometry headlessly; nothing exercised `_attachXrPanel` live. **This is a minor bump, so `RELEASING.md` step 5a requires a human driving every demo flat AND in VR** — and the headset pass happened *before* these fixes landed. The post-fix state is unvalidated, and the 4th headset finding (panel reposition) was deferred rather than built. M3 should be fixed before that pass so it is exercised in the same run.
3. **No `v0.8.0` tag, three `[release] v0.8.0` commits.** Resolve to one commit and one tag; re-point the tag at HEAD immediately before publishing, per step 7.
4. **`registerIcons`' precedence rules were never reviewed.** A new page-global mutable registry shipped in a minor: registering `trash` silently and permanently replaces the shipped icon for every `<tosi-b3d>` on the page, with no warning, no scoping and no un-register. Covered by the two TODO items above, but flagged here because the *decision* (is last-write-wins the policy?) has not been made, only implemented.
