## BLOCKERS (must fix before tagging)

### B1 — Popup title-bar drag never engages; Babylon releases it on the pointerdown that starts it

`src/popup-surface.ts:554` · _correctness, verified with NullEngine_

With the default `gripHeight: 0.2`, `attachDrag` sets `startAndReleaseDragOnPointerEvents = false` (:532) and `wirePointer`'s `onPrePointerObservable` handler calls `drag.startDrag(pointerId)` (:554). `startDrag()` sets `dragging = true` but leaves `_activeDragButton = -1`; Babylon then fires `onPointerObservable` POINTERDOWN, whose own observer runs `if (dragging && sameId && evt.button !== -1 && evt.button !== _activeDragButton && !allowOtherButtonsDuringDrag) releaseDrag()` — button 0 ≠ -1, so the drag dies inside the same event. Reproduced headlessly: one `onDragStart`, one `onDragEnd`, zero `onDrag`, mesh never moves. User-visible: press a title bar, the popup tears off and jumps to front but never follows the pointer. **Drag/tear-off is a headline 0.7.0 feature and `gripHeight: 0` (non-default) is the only working path.**

**Fix:** start the drag after Babylon's own POINTERDOWN pass — move the grip hit-test from `onPrePointerObservable` to `scene.onPointerObservable`, or defer `startDrag` with `queueMicrotask`. **Do NOT set `allowOtherButtonsDuringDrag = true`** — that same branch is what releases the drag on pointerup while `startAndReleaseDragOnPointerEvents` is false, and the popup would then stick to the cursor forever. **Companion defect one line away:** with `startAndReleaseDragOnPointerEvents = false`, the behaviour's POINTERUP branch is also gated off, so nothing calls `releaseDrag()` — `wirePointer` must release on POINTERUP too. Add a NullEngine regression test asserting `drag.dragging === true` after a simulated POINTERDOWN.

### B2 — The close-× hit region is disjoint from where the × is drawn

`src/popup-surface.ts:351` · _correctness/coverage, verified_

The glyph is drawn at `x = vbW - glyph - pad` with `glyph = min(barH*0.62, vbW*0.09)` and `pad = (barH - glyph)/2` — a **height**-derived inset applied on the **x** axis. The hit test is `uv.x > 1 - gripFraction * 0.55`, where `gripFraction` is a fraction of **height** and `uv.x` is a pure width fraction. For a portrait viewBox 200×600 at default `gripHeight 0.2`: the × occupies u ∈ [0.655, 0.745] while the close region is u > 0.89 — **fully disjoint**. Clicking the visible × falls through to `beginDrag`, and since `draggable` defaults true and `onDragStart` calls `tearOff`, **clicking close tears the popup off its opener**; clicking empty bar space at the far right closes it. Square 300×300 splits the glyph down the middle. The shipped demo's 220×130 landscape card happens to be one of the few aspects where it works, which is exactly why it went unnoticed. (The move glyph is mispositioned by the same `pad` but stays inside the drag region for sane aspects — cosmetic there.)

**Fix:** derive the glyph rect and the hit thresholds from **one pure helper** in viewBox units (`chromeGlyphLayout(vbW, vbH, gripHeight)` + `popupHitRegion(uv, …)`, in the style of `flow-layout`/`hud-math`), and unit-test that the close region _contains_ the drawn glyph bounds and excludes the move glyph across wide/square/portrait × gripHeight 0/0.2/0.5. The module doc at :115 currently claims "the hit regions this module tests against" — nothing tests them.

### B3 — `library.instantiate()` / `lib.make.*` rotation is silently discarded unless `canonical: true`

`src/b3d-library.ts:543` · _correctness, verified against the shipped `static/test-3.glb`_

`instantiate` writes `result.rotation.x/y/z`. On the non-canonical (default) path `result` is a clone of the glTF node, and Babylon's loader **always** assigns `rotationQuaternion` (`_LoadTransform` sets `Quaternion.Identity()` even with no rotation in the file); `TransformNode` ignores `.rotation` entirely while a quaternion is present. Measured on the real scout: `ry = 0`, `ry = 140` and `ry = -90` all yield **bit-identical** forward vectors — you get the GLB's own baked scene rotation (~−113.9° yaw) regardless. `position` works; only rotation is lost. So `lib.make.scout({ y: 0.9, ry: 140 })` — the b3d-collisions demo **shipping in this release** — rotates by nothing, in either unit, and CHANGELOG:62–66 asks adopters to "multiply by `180 / Math.PI`" for an option that has never had an effect on this path. This is pre-existing (v0.6.2 has the same line in radians), but 0.7.0 is what advertises it.

**Fix:** write the rotation as a quaternion the way `make-mesh.finish` already does (`Quaternion.RotationYawPitchRoll(ry*DEG, rx*DEG, rz*DEG)`), or null `rotationQuaternion` before writing euler. `library-animations.test.ts` already stands up happy-DOM + NullEngine + `test-3.glb` — reuse that harness to assert a non-canonical `instantiate('scout', { ry: 90 })` actually yields a 90° world forward (and that 90 is not treated as radians).

### B4 — The 0.7.0 CHANGELOG is structurally broken — and it's the only migration channel consumers get

`CHANGELOG.md:50, 67, 89, 112, 449, 472` · _docs/dx/blast-radius, verified_

Five defects in one document, all reproduced:

1. The intro ends **mid-clause** at line 50 ("Read the ⚠️ Breaking block before upgrading a scene") and its tail — "that was tuned around the old feel." — is glued on at line 67 as the last line of the `library.instantiate()` **migration instruction**, where it reads as part of it. The diff shows the mechanism: the line was removed from under the intro and re-emitted at the tail of a newly inserted bullet.
2. **Both silent radians→degrees breaks sit at lines 52–66, ABOVE `### ⚠️ Breaking` (line 69).** The Breaking block never mentions degrees. A reader who does what the file itself instructs — jump to that heading — misses the two changes most likely to break them **with no error**.
3. **Two `### Added` headings inside 0.7.0** (lines 112 and 449, straddling `### Changed` at 421). The second is the pre-refactor `el.make.*` entry: "Covers box/sphere/cylinder/plane/ground/disc/torus/capsule" — the hand-written eight that commit `0a1a11f6` replaced with a Proxy — directly contradicting the line-124 entry saying all 26 MeshBuilder shapes are reachable. A reader hitting the second first concludes `make.icoSphere` doesn't exist.
4. Breaking:89 says "The glass gamepad hides itself once a **mouse**, keyboard or hardware pad is used"; Fixed:472 says "The glass gamepad **no longer fades when you move the mouse**." One release, two opposite statements about the same default.
5. **Nothing in the published artifact carries any of it.** `npm pack --dry-run --json` → 506 files, only `dist/**`, `README.md`, `package.json`. No CHANGELOG, no `Migration.md`, and `grep -i 'changelog\|migration\|upgrad' README.md` → nothing. The practices test is explicit (`releasing.md:227`): _"Can a consumer who has only what they installed find the migration table? If not, it doesn't exist for them."_ Today it doesn't.

**Fix:** repair the intro sentence and delete the orphan; move both degrees bullets into `### ⚠️ Breaking`; merge the line-449 block into line 112 and drop the stale eight-shapes text; correct the glass-gamepad bullet to keyboard-or-hardware-pad only. Then add a root `Migration.md` (0.6.2 → 0.7.0 before/after table: both degrees changes, `hudChase`→`hudChaseOff`, `getNames()` string shape, glass-gamepad fade, right stick), add it + `CHANGELOG.md` to `package.json` `files`, and put an `## Upgrading` line near the top of README linking both with **relative** paths so they resolve inside `node_modules`. Verify with `npm pack --dry-run --json`.
