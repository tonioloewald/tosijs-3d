## 🔴 Blocker (1)

### B1 — The 0.8.2 "snow line tracks the sea level" fix never reaches the shader; the reported snowcaps still reproduce at HEAD

_Merged from three findings — `src/world-sim.ts:165` (correctness, blocker, verified) + `src/world-sim.ts:165` (blast-radius, blocker, verified, one wording kept: "fixed in the demo rather than in the layer every consumer shares") + `src/b3d-terrain.ts:285` (blast-radius, major, verified). One defect; three surfaces._

**Mechanism (re-confirmed by source inspection in this triage).** `biomeSeaLevel` / `biomeLapseRate` / `biome` are read in exactly one place — `createMaterial()` (`src/b3d-terrain.ts:900-918`) — and `createMaterial()` has exactly one call site, `sceneReady` (`src/b3d-terrain.ts:767`). The value the shader actually sees is `biomePlugin.params.seaLevel`, re-read every bind by `bindForSubMesh` (`src/biome-plugin.ts:412-419`) — and **nothing in `b3d-terrain` ever writes it**: `_rebuild()` (`src/b3d-terrain.ts:1913-1926`) touches only `material.wireframe`, `render()` only compares generation keys, and `biomePlugin` is never attached lazily. The seam is live and free; it is simply never fed.

**Measured (adversarial verification, NullEngine against the real element):** after `biomeSeaLevel = 320` + `regenerate()`, `attr` reads 320 while `plugin.params.seaLevel` stays 80 — through repeated `regenerate()` calls — while a direct `plugin.params.seaLevel = 320` takes effect immediately. With defaults (0.72 / 0.004) the chart's cold/snow column begins 180 m above the anchor, so a stale 80 m anchor under a 240 m waterline puts the snow line **at the waterline and above**: every island is a snowcap, exactly as reported.

**Cost is not free.** Both biome attributes are in `_generationKey()` (`src/b3d-terrain.ts:1859-1861`), and the demo writes `terrain.biomeSeaLevel` **after** calling `terrain.regenerate()` (`src/world-sim.ts:157-166`), so the adopted key is stale the moment the write lands — measured 52–93 extra tile re-cuts of an 80-tile pool for a single slider step, a second full-pool re-cut for a value the shader never sees. Counterfactuals measured zero extra builds with no write and zero with the write ordered before `regenerate()` — the cost is the ordering, not the dial.

**The commit's claim does not hold.** `ccf5da37` says it wires `biomeSeaLevel` "on both creation and every dial change"; it changed only `src/world-sim.ts` (+5 lines) and never `src/b3d-terrain.ts`, and the dial-change half is measurably inert. The same dead seam covers `biome = 'on'` at runtime (plugin stays `null`) and a live `biomeLapseRate` write (params stays constructed).

**Blast radius (the folded major).** The attribute row says "keep it equal to your water plane's `y`" (`src/b3d-terrain.ts:285-286`, mirrored verbatim into the shipped generated index `static/attributes.txt:908-909` — the adopter entry point), `scene-schemas.ts:490-491` vends both as ordinary ranged controls, and `terrainEditor3d` lists them in its BIOME group (`src/terrain-editor.ts:148,166-167`). So the no-op spelling is the documented and discoverable one, while the working spelling (`biomePlugin.params.seaLevel = v`, as `biome-chart`'s own demo does) is documented nowhere near it. `biomeLapseRate` is the structural twin, not a separate bug.

**This is the user's bug, still open, in the release that claims to fix it.**

**Remediation (re-review scope: correctness + blast radius over the remediation diff only):**

- `src/b3d-terrain.ts` — sync the plugin params from the attributes in `render()`/`_rebuild()` after the key check (`if (this.biomePlugin) { this.biomePlugin.params.seaLevel = a.biomeSeaLevel; if (a.biomeLapseRate > 0) this.biomePlugin.params.lapseRate = a.biomeLapseRate }`); attach the plugin lazily from `render()` when `biome` flips to `'on'`; **remove `biomeSeaLevel`/`biomeLapseRate` from `_generationKey()`** (they are not generation attributes) — otherwise every sea-level drag keeps re-cutting tiles.
- `src/world-sim.ts` — move the `biomeSeaLevel` write **before** `regenerate()` so the two-rebuild guard holds.
- Test on the existing harness (happy-dom + NullEngine, `src/terrain-regenerate.test.ts` pattern) asserting `el.biomePlugin.params.seaLevel` follows the attribute. The current suite asserts rebuild counts only — which is precisely why this dead seam passed, and `doc-examples.test.ts` parses/import-checks snippets but never executes them, so a doc example cannot catch it.
- Per gate 6: every prior green on the biome-adjacent suite was measured with **no readout of the uniform** — re-run it after the change.

_If the team instead keeps these construction-only, then: drop them from `_generationKey()`, delete the demo's write, and say "construction-time" on the attribute row — but that leaves the editor, the schema and the index publishing a knob that does nothing, so making them live is the smaller change._

## Follow-ups

### → Fix now, as part of B1's remediation (correctness)

- [ ] **M3 — `src/world-sim.ts:61` — the demo never scales `biomeLapseRate` to its vertical range.** _(unverified finding; independently corroborated here: the element's own attribute comment, `src/b3d-terrain.ts:473-478`, says it "MUST be scaled to `grossAmplitude`… 0.5 / amplitude gives temperate valleys and cold summits", and the demo leaves the 0.004 default.)_ With the 0.004 default the snow column begins ~180 m above sea level while the `v size` dial runs to 400 m, so **fixing the seam alone still leaves snowcaps on the peaks** — the reporter could reasonably report the bug as unfixed. Set `biomeLapseRate: 0.5 / demo.grossAmplitude` and update it in the same observer loop. Leave the shipped 0.004 default alone; it is the small-world value other adopters rely on.
