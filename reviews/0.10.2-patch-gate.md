## Fix before the tag (verified major)

### 1. Decorator seating computes the mesh cell without `horizScale` (verified)

`src/b3d-decorator.ts:771-773` (blast-radius major; the correctness lens reported the same defect as a minor at line 772 — merged here)

- **Defect:** `cell = terrain.tileSize / max(1, terrain._resolvedSubs || 16)`. The drawn cell is `tileSize * horizScale / subs` (`src/b3d-terrain.ts:1207-1208`), so the value is short by exactly `horizScale`.
- **Effect:** Land and Sky runs `horizScale: 3.31`, so the sampling ring is about 0.21 of a drawn cell instead of 0.7. The dip grows roughly with the square of the radius, so the correction is about a tenth of what was intended, and rocks still float in the demo the fix was made for. With `horizScale` below 1, items are over-buried. The default of 1 is correct.
- **Also:**
  - Placements on coarser LOD tiles (cells 2x or 4x larger) are under-corrected the same way.
  - The decorator reads the terrain's `private _resolvedSubs` through an untyped reference.
  - No test covers the seating.
- **Not checked:** this was confirmed from source, not in a running scene. The claim that spawner, prefabs and `placeOnSurface` have the same floating problem is a design observation, not checked caller by caller.
- **Fix:** multiply by `(terrain.horizScale || 1)`. Better: expose the drawn cell size on the terrain as a public getter next to `drawnReach` (for example `meshCell` or `drawnHeightAt(x, z)`) and have the decorator call it.
- **Check that clears it:** extract the tangent-plane dip as a pure function and add a unit test with a `horizScale != 1` case that fails with the fix reverted. Or drive Land and Sky at `horizScale` 3.31 and confirm rocks sit on the drawn mesh.
- No re-review needed.

## Minors

### Verified

**2. Airless fog now ends at the terrain's drawn reach and blacks out everything beyond it, not only the terrain edge (verified; severity was uncertain, confirmed minor)**

`src/b3d-skybox.ts:~2639-2670`

- **What changed:** at full vacuum with a `tosi-b3d-terrain` present, the space fog layer goes from 1e6..1e7 to 0.66*reach..reach in black. These are scene-global fog values.
- **Mode 1:** any fog-enabled mesh further than `reach` from the camera (a distant base, another craft, a StandardMaterial planet) is fully black. Default terrain reach is about 560 m.
- **Mode 2:** vacuum also rises with camera altitude (`spaceStart`/`spaceFull`), so climbing out of an Earth-like atmosphere above a terrain blacks out the ground once altitude exceeds the reach.
- **Qualifier from verification:** it only bites when `scene.fogMode` is linear, i.e. a `<tosi-b3d-fog>` with its default mode. With no fog element, or with exp/exp2, there is neither the regression nor the intended terrain-edge fade.
- **Shipped-demo exposure is small:** Land and Sky's Airless presets have reach 5000 with linear fog; rocket-ascent uses `b3dGround`, so its reach is 0.
- **Not checked:** read from code, not driven in a browser. No test covers either mode.
- **Owner call:** if only the terrain edge should fade, apply the fade to the terrain's material (or use horizontal distance), or leave the layer at the far values when vacuum comes from altitude.

### Unverified (leads; sanity-check before acting)

**3. `regenerate()` leaks one ring ShaderMaterial per call (unverified)** — `src/b3d-planet.ts:796`
- The lens measured on `/gas-giant/`: 13 `planet-ring-mat` materials right after mount, 37 after about two dozen dial changes, while `gas-giant` stays at 1.
- The diff fixed the planet mesh (`dispose(false, true)`), but the ring, atmosphere and ocean meshes still dispose without their materials.
- The headline demo calls `regenerate()` on every slider or colour tick.
- Fix: dispose those three with their materials; optionally coalesce the demo's rebuild into one per tick.

**4. The "amount" ring slider in the gas-giant demo does nothing between 0.05 and 1 (unverified)** — `src/gas-giant.ts:66`
- The lens measured: setting `rings` to 0.3 on Neptune left `ringOpacity` at 0.07.
- The demo always passes explicit `ringOpacity` and `ringOuter`, which bypass `rings` in `buildRings`.
- The planet docs say `rings` scales the preset's brightness, which holds only when `ringOpacity` is -1.
- Fix: drop the slider, or make an explicit `ringOpacity` still multiply by `min(1, rings*1.2)`, and say which on the attribute row.

**5. Ring code exists in two drifted copies (unverified)** — `src/b3d-star-system.ts:611`
- `b3d-planet` moved to a `planetRing2` shader with per-preset ring shape, colour and opacity.
- `b3d-star-system` still registers the old `planetRing` shader with the old rule; its "shared with b3d-planet" comment is no longer true.
- A star-system giant with the Jupiter, Uranus or Neptune look carries a broad bright Saturn-style ring.
- The ring is parented to the giant mesh, which now has `scaling.y = 0.93`, so the tilted ring is slightly sheared.
- Fix: one ring builder used by both, taking `resolveGasGiant(kind).rings`; parent the star-system ring to an unscaled node.

**6. `SwatchStore.add()` saves a colour that is already offered, returns true, and reorders the grid (unverified)** — `src/color-presets.ts:168`
- The interface says `add()` returns false if the colour was already offered; it only checks its own `added` list.
- The lens measured: `store.add(COLOR_PRESETS[0])` returned true and pushed `#e8e8e8` into `added`.
- In the UI: pick a default swatch, press +, and it jumps to the front, persisted in localStorage for every picker on the page. Same for a colour from the caller's `presets`.
- Fix: return false when the value is in `COLOR_PRESETS` and not in `removed`; have the picker skip the add when the colour is already in `list()`; add the case to `color-presets.test.ts`.

**7. `colorPicker3d` always persists to the shared localStorage store (unverified)** — `src/color-picker.ts:358`
- `openPopup` hard-wires `sharedSwatches()` and `ColorPicker3dOptions` has no store option, so the exported `createSwatchStore(storage)` cannot reach a picker.
- An adopter keeping its own document (ensemble) cannot redirect or disable the writes.
- The key is per origin, so two tosijs-3d apps on one origin share swatches.
- `remove()` appends to `removed` for colours nobody supplies, so that list only grows.
- Fix (additive): a `swatches?: SwatchStore | null` option (null = session-only); document the key and the opt-out; only record a removal when presets still supply the colour.

**8. The star-system light change is listed under Fixed without the "(behaviour)" mark 0.10.1 used (unverified)** — `CHANGELOG.md:60`
- Intensity went from `min(L*0.5, 5)` to `clamp(1.6 * L^0.25, 1.2, 3.5)`.
- A sun-like star goes from 0.5 to 1.6 (about 3.2x brighter); the top end drops from 5 to 3.5.
- Gas giants in a system also change look (banded shader, 0.93 flattening).
- The entry describes the K-star case only.
- Fix: mark it "(behaviour)" and state old and new intensity for a sun-like star; consider a `starLight` multiplier attribute (default 1).

**9. Several behavioural changes ship with no test that fails without them (unverified)** — `src/color-picker.ts:233`
- `colorPicker3d` is 440 lines of stateful widget (open tracking, toggle-to-close, close-and-reopen on resize, delete mode, bound-value sync) with no test file, while sibling widgets have them.
- Also untested: decorator seating maths, ground-frame moon direction and spin-axis maths, the star light-intensity curve, the mantle landing following a moving surface.
- Not a blocker by rule (a missing test never blocks).
