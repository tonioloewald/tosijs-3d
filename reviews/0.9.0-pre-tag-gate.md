## 🔴 Blockers — fix before the tag (5)

### B1 — `b3d-prop`'s module-global `libraryUrl` cache breaks every scene after the first
`src/b3d-prop.ts:118` — *confirmed*

`mounted` is a `Map<url, {type, el}>` keyed by URL only. `_resolveLibrary` (`:196`) returns the cached `type` **before** the `owner.appendChild(el)` at `:205`, with no owner check. `B3d.getLibrary` reads a per-instance `_libraries` map (`tosi-b3d.ts:1680`). So on a page with two `<tosi-b3d>` sections sharing a `library-url`, scene B gets `__prop-0`, never mounts a library into itself, polls for 5 s, logs `b3d-prop: no <tosi-b3d-library type="__prop-0"> in this scene after 5s` and renders nothing. Same on any SPA/doc-browser re-mount — the cached entry points at a detached element from a disposed scene, and nothing ever deletes it, so the URL is permanently poisoned.

This is verbatim the use case the element's doc sells (a raw-HTML scroll narrative of sections = multi-scene by construction), and `b3d-prop` is new in this release.

**Fix:** key the cache per-owner (`WeakMap<B3d, Map<string,string>>`), drop the entry on `whenDisposed`. Add a two-owner test.

### B2 — The activation veto is fed stale/synthetic info, so a reach veto fails open
`src/interactive-behavior.ts:179` — *confirmed*

`_last` is written only on a pointer hover of this behavior's own meshes (`:242`) and initialises to `{mesh:null, point:null, distance:0}`.

- **(a) Fail-open.** The shipped doc example veto `(info) => info.source !== 'near' && info.distance > 2` sees `distance: 0` for an NPC 50 m away calling `activate({actor})` on a never-hovered door → `0 > 2` false → the door opens. `useNearest` is no better: `nearestInteractive` computes the true `bestDist` (`:322`) and **discards** it (`:327`). The one scenario the feature's doc sells — "a lock you can REACH is not a lock you can merely SEE" — is the one it cannot decide.
- **(b)** `{ source:'api', ...this._last, ...info }` spreads `_last` *after* the default, so after any hover a bare `activate()` reports `source:'pointer'`, contradicting the comment one line above.
- **(c)** `operable` (`:166`) and `debugState` (`:193`) use the **opposite** spread order, so `operable === true` does not imply `activate()` will fire, and the debug readout can report `ok` for a veto that blocks.

The pointer path is fine (`_fire(this._last)` carries a real `pick.distance`) — what's broken is exactly the two paths the feature was added for.

**Fix:** one spread order everywhere (`{...this._last, source:'api', ...info}`); thread `bestDist` through `useNearest`; a bare `activate()` with no supplied distance should carry `undefined`/`Infinity` so a reach veto **fails closed**. Add a behavior-level test — `interaction.test.ts` only exercises the pure function with hand-built info, i.e. the half that works.

### B3 — `parseColor` throws on prototype-chain keys (fixed on the icon side, missed here, same diff)
`src/color.ts:101` — *confirmed*

`const named = NAMED[s]` — `NAMED['constructor']` returns `Object`, `??` doesn't fire, `text.startsWith` throws `TypeError`. Reproduced: `parseColor('constructor')`, `parseColor('__proto__')`, `parseColor('CONSTRUCTOR')` all throw where `parseColor('#zz')` correctly returns `null`. The contract is explicitly fail-closed ("Returns `null` rather than guessing").

Three shipped call sites, all reproduced live: `keyboard.ts:886` (`paint()`, every keystroke of `inputField({type:'color'})` — typing `constructor` throws on the final `r`, and `isValidForType`'s `/^[a-z]*$/i` does not catch it); `key-layout.ts:297`; `color-field.ts:163` (throws at construction on a document with `color: "constructor"` — the headless-validation path `color.ts`'s own header advertises). **Plus one the finding missed:** `inputField({type:'color', value:'constructor'})` throws at construction, and `setValue('__proto__')` throws.

Per CLAUDE.md there is no console in a headset — this is a VR panel that dies silently. Meanwhile this same diff added `register-icons.test.ts` with a dedicated `describe('icon names that collide with Object.prototype')` and hardened `svg-icons.ts:238` with `Object.hasOwn`.

**Fix:** `const named = Object.hasOwn(NAMED, s) ? NAMED[s] : undefined`, keep the `typeof` narrowing, extend `color.test.ts`'s `'garbage returns NULL'` list with `constructor`/`__proto__`/`CONSTRUCTOR`.

### B4 — #48's rotation fix reached 2 of 5 library-load sites; launcher shells fly backwards
`src/b3d-launcher.ts:978`, `src/b3d-turret.ts:250` — *confirmed*

`LibraryMeshRequest.transform` makes `rx/ry/rz` **optional**, and that seam is where the bug re-entered. Both sites pass `transform: { x, y, z }` only and neither calls `this.render()` in `onLoaded` — the two things `b3d-prop.ts:182` and `b3d-destroyable.ts:396` do deliberately ("the component render that would have synced the transform has already run"). Both classes spread `AbstractMesh.initAttributes`, so `rx/ry/rz` are real and writable. `AbstractMesh` syncs rotation **only** in `render()` — there is no per-frame sync — which is why the placeholder path works and the async library path doesn't.

Concrete: `b3dLauncher({ library:'weapons', meshName:'cannon', ry:180 })` — `forward()` returns `mesh.getDirection(Z)` on an unrotated node, so shells fly the opposite way, silently, while the same element **without** `library` fires correctly. `library` on turret/launcher is new in this release (`bf84801a`, #34), so this ships as a first impression.

Two refinements from verification: **turret** needs a design decision, not the launcher's one-liner — `_update` overwrites `_barrel.rotationQuaternion` every frame, so naively forwarding `rx/ry/rz` would break the aim math. And `b3d-aircraft.loadFromLibrary` (`:1969-2007`) is an unmigrated structural twin — no `scale`, no bounded wait, no missing-library error, and a `library-changed` listener on `owner` with **no disposal path** (`sceneDispose` `:2174-2220` never removes it), so an authoring typo fails silently forever.

Also: `library-mesh.ts`'s own doc still says "One implementation, used by b3d-prop and b3d-destroyable" and "this loader lives in exactly one place" — both false in-tree, and republished verbatim at `llms.txt:222`. A future reader will trust it and fix in one place again.

**Fix:** make `transform`'s rotation fields **required** (or have `loadLibraryMesh` take the calling `AbstractMesh` and read/sync itself), so a call site cannot silently omit them. Migrate or record a keep-decision for the aircraft twin. Correct the doc.

### B5 — The new attribute index omits every inherited attribute, and README now calls it authoritative
`bin/attribute-index.ts:76` — *confirmed (verifier adjusted blocker → major; "I'd fix before the tag")*

`docComment()` requires the file to start with `/*#`. `src/b3d-utils.ts` doesn't, so its doc comment is never sliced off and `declaredAttributes()` latches onto the first **textual** `static initAttributes` — line 678, inside a doc-comment code example (`{ color: '#ff8800' }`). Zero keys → the module is skipped → the real `AbstractMesh.initAttributes` at `:799` is never reached.

Verified in the shipped artifact: `grep -c '^  rx' static/attributes.txt` → **0**. `b3d-prop` lists four attributes (`library`, `libraryUrl`, `meshName`, `scale`) and no way to position or rotate it. **14 elements** inherit `x/y/z/rx/ry/rz` this way.

A second, independent defect the finding did not name: `tableRows()`'s regex takes one backticked name per row, so `b3d-prop.ts:69-70`'s `| \`x\` \`y\` \`z\` |` rows are silently dropped — the index discards authored documentation from the very page it indexes.

`README.md:9-13` and `llms.txt:301` both now instruct readers to "Search the attribute index before assuming it does not exist". This reproduces, inside the index, the exact failure it was built to end — a confident wrong answer instead of no answer. `attribute-index.test.ts` cannot catch it: its gates are `index.length > 40` (63) and `total > 400` (688).

**Fix:** find the first `/*#` block anywhere (or strip comment regions before scanning); split multi-name table rows; emit inherited attributes for spread bases. Add `expect(find('b3d-prop').attributes).toContain('rx')`. Regenerate `static/` + `docs/` artifacts.

## 🟠 Confirmed majors — fix, or record an explicit defer with a named owner (2)

### M6 — Terrain runs an unbounded full-pool rebuild on every attribute-change render
`src/b3d-terrain.ts:1724` — *confirmed*

`render()` compares `_generationKey()` and calls `regenerate()` inline; `regenerate()` does `clearPool(); update(this.pool.length)`; `update()` passes `msBudget = 0` for a budgetOverride ("deliberately unbounded"), and `streamTiles` guards its break on `msBudget > 0`, so the per-frame time cap is genuinely disabled. tosijs's attribute setter calls `queueRender()` (one rAF), `slider3d` sets on every `move`, and the shipped `terrainEditor3d` demo writes attributes straight through — so a drag is **one full rebuild per animation frame**.

Measured with the repo's own `PerlinNoise` under Bun on this Mac: ~50 ms of noise alone at the high tier (120 tiles × 25² verts) against `tileBuildMs: 4` / `fillBudget: 24`, and ~6.3 ms at the quest tier inside a 13.9 ms VR frame — before skirts, normals and 56–120 `updateVerticesData` uploads. `perf-probe.ts`'s own comment: "a dropped frame is nausea, not jank."

Secondary: `regenerate()` never updates `_genKey`, so the documented "set attributes, then call `regenerate()`" pays **two** full rebuilds. `terrain-regenerate.test.ts` is a mirrored harness that pins the burst case and never exercises the across-frames one — which is what a drag is.

**Fix:** keep the unbounded rebuild for the explicit `regenerate()` API; make the render-triggered path budgeted (clear the pool and let `update()` stream it back under `fillBudget`/`tileBuildMs`) or debounce it (~150 ms with a trailing rebuild). Then check `worstFrameMs` stops spiking during a drag.

### M7 — Nine new test files re-implement the production logic they claim to cover
cross-cutting — *confirmed*

Eight of the nine import **zero local modules** (verified by grep for `from './` / `import('./`): `aircraft-rig`, `destroyable-library`, `scene-panel-dismiss`, `skybox-sun-race`, `spawner-anchor`, `terrain-budget`, `terrain-regenerate`, `b3d-beacon`; `frame-info`'s two-clocks block re-implements `tick` locally. A file that imports no local module cannot observe a change to one — the "revert the fix, suite stays green" property is proven statically.

Concretely: delete `this._applyChaseGeometry()` from `b3d-aircraft.ts:1310` and #43 is fully reintroduced with **2190/2190 still passing**; set `MAX_TILES_ACROSS` to 100000 and `terrain-budget` still passes; drop `rx/ry/rz` from `loadLibraryMesh`'s `instantiate` call and #48 returns green. Each duplicated constant (`MAX_TILES_ACROSS = 256`, `LIMIT = 300`, the 22-attribute generation key) is also a second address that drifts silently.

`library-mesh.ts` — the shared loader `b3d-prop`, `b3d-destroyable`, `b3d-turret` and `b3d-launcher` all depend on, exported at `index.ts:1091` — has **no direct test at all**, despite taking a duck-typed `owner` and plain callbacks (nothing about it needs a DOM). Both B1 and B4 live in code it covers.

Proportionality: 13 of the 22 new test files *do* import real modules, so this is a subset — but it is precisely the subset covering the adopter-reported fixes (#40/#41/#43/#47/#48/#49/#55/#66) this release exists to deliver. Two overclaims noted and set aside: `b3d-beacon.test.ts` is a genuine Babylon-semantics characterization test (though flipping `visibility = 0` → `isVisible = false` still leaves it green), and only `aircraft-rig`'s final block is tautological.

**Fix:** drive `loadLibraryMesh` headlessly with a stub `owner.getLibrary` (pins rotation forwarding, the generation guard, the retry-stop — and B1/B4); export `MAX_TILES_ACROSS` and lift `_budgetedReach`/`_generationKey` so they can be asserted directly. Where a Babylon rig is genuinely needed, at minimum **import the constant** instead of restating it.
